# پاسخ احوال‌پرسی و رفع تکرار فرم بدون نتیجه

**گزارش کاربر:** واردکردن «چطوری» در چت دستیار خرید، به‌جای پاسخ کوتاه، مسیر جست‌وجوی محصول را آغاز می‌کرد و عبارت بدون کالای مطابق، سه پیام «با این شرایط گزینه منطبقی پیدا نشد» تولید می‌کرد.

## تشخیص
- `isGreetingOnly()` در React فقط «سلام چطوری» را پوشش می‌داد، نه «چطوری» به‌تنهایی.
- `render_results_node()` در بک‌اند برای جست‌وجوی بی‌نتیجه به‌درستی `empty_state` و فرم قابل اصلاح صادر می‌کرد؛ اما رندرر هم متن `assistant.message` و هم عنوان `empty_state` و هم `SchemaForm` با همان عنوان را نشان می‌داد.
- پیام احوال‌پرسی و سؤال‌های دقیق درباره **راهنمای استفاده از همین دستیار** نیازی به فراخوانی BoxAPI، جست‌وجوی دیتابیس یا ایجاد مأموریت جدید ندارند.

## اصلاح
- نگاشت بسته و محدود برای «چطوری»، «خوبی» و احوال‌پرسی‌های ساده؛ درخواست خرید مثل «چطوری یه لپ‌تاپ مناسب انتخاب کنم» همچنان وارد جست‌وجوی محصول می‌شود.
- راهنمای کوتاه استفاده برای «راهنما»، «چطور ازت استفاده کنم» و جمله‌های هم‌معنیِ مشخص، بدون مصرف اعتبار API.
- در حالت `empty_state` متن تکراری پیام از دید حذف می‌شود؛ عنوان داخلی فرم نیز حذف می‌شود، ولی فیلدها، شرایط سخت، توضیح اصلی و اقدام «جست‌وجوی دوباره» حفظ می‌شوند.
- تست‌های واحد مربوط به تشخیص مکالمه و کنترل UI؛ سناریوی Playwright برای «چطوری»، «راهنما» و عدم تکرار فرم.

**محدودیت:** این مسیر احوال‌پرسی/راهنما در اپ React به‌صورت محلی پاسخ می‌دهد و مثل سایر احوال‌پرسی‌های موجود در mission backend persist نمی‌شود. برای درخواست API مستقیم بک‌اند، routing مکالمه هنوز بخشی از پروژه آینده است.

## وضعیت
یک شاخه و یک PR متمرکز، با یک اجرای CI در زمان ready. فایل‌ها و migration دیتاست تغییری نکرده‌اند.


## گسترش محافظت در برابر خطا (تغییرات بعد از بازبینی)
- طبقه‌بندی محلیِ محدود برای سلام/راهنما/تشکر/خداحافظ؛ پشتیبانی از شکل عربی «ك/ي» و نیم‌فاصله؛ حفاظت از عبارت‌های واقعی خرید.
- محافظت هم‌زمانی با ref در React پیش از commit شدن `isRunning`، جلوگیری از دو POST با دو فشار سریع Enter.
- در `sendMissionTurn`، نبود `turn.completed` یا کارت نتیجه دیگر «موفقیت» تلقی نمی‌شود؛ SSE با سقف buffer و شناسه مأموریت/نسخه قرارداد اعتبارسنجی می‌شود.
- در قطع SSE پس از commit سرور، `GET /missions/{id}/` می‌تواند نتیجه را از snapshot بازیابی کند، بدون تکرار خودکار فراخوانی BoxAPI یا درج دوباره رویداد.
- در خطای شبکه، متن درخواست در composer باقی می‌ماند؛ «بازیابی وضعیت» جای ارسال دوباره خودکار پیشنهاد می‌شود.
- retry استعلام نمایشی فروشنده از همان `client_request_id` استفاده می‌کند تا تلاش ناموفق شبکه به استعلام تکراری با نتیجه جدید تبدیل نشود.
- خطاهای HTML 502/503/504 و محدودیت 429 به پیام انسانی تبدیل می‌شوند؛ JSON اشتباه با متن قابل‌فهم گزارش می‌شود.
- `turn.completed.search_query` به React اجازه می‌دهد query واقعاً تفسیرشده را با شرایط مؤثر از سرور هماهنگ کند.
- حداکثر طول فیلدهای فرم با محدودیت‌های Django مطابقت پیدا کرد.

### سناریوهای جدید با تست
- راهنمای کوتاه، سلام با عربی/فارسی و نیم‌فاصله، تشکر، خداحافظ، و عدم بلعیدن جمله‌های دارای نیت خرید
- قطع استریم، نبود رویداد پایان، رویداد مأموریت دیگر، HTTP 502/429/404، JSON نامعتبر
- ادامه از snapshot صرفاً برای turn کاملِ اخیر، نه turn قدیمی
- دو کلیک/ارسال سریع، تعهد به کلید idempotency فروشنده، حفظ فرم و متن پس از شکست

**توجه:** تمام این‌ها پوشش رگرسیونِ پیاده‌سازی هستند؛ تا وقتی CI روی این head سبز نشده، ادعای قبولی ندارند.

## گیت کیفیتِ اولین اجرا
در اجرای اولیه PR #24 فقط یک تست رشته‌ای در `contextual-ux.test.ts` نام تابع را از فایل اشتباه بررسی می‌کرد؛ تست‌های دیگر و browser-journey سبز بودند. پس از تغییر از دو predicate به classifier واحد، assertion با رابط تازه هماهنگ شد. سناریوی راهنمای Chromium نیز با متن واقعی راهنمای UI تطبیق داده شد. این اصلاحات در همان PR تجمیع می‌شوند و گیت‌ها در پایان روی head جدید دوباره اجرا می‌شوند.

### تاریخچه گفتگو و فرم‌های قدیمی
درخواست محاوره‌ایِ محلی نباید فرم آخرین جست‌وجوی ناموفق را غیرفعال کند. در عوض، پس از شروع یک جست‌وجوی واقعی جدید، فرم‌های قبلی به توضیح متنی کوتاه تبدیل می‌شوند تا صفحه با فرم‌های غیرفعال و تکراری شلوغ نشود. نتیجه‌ها و شروط واقعی جست‌وجوی جدید همچنان معتبر می‌مانند.

## مواردی که این PR هنوز تضمین نمی‌کند
- قطع واقعی برق سرور، packet loss در محیط production و استقرار عمومی HTTPS؛ نیازمند load/chaos test کنترل‌شده پس از استقرار.
- اعتبار مصرف BoxAPI در برابر کاربران ناشناس عمومی باید با quota/rate limit مستقل در بک‌اند حفاظت شود.
- محدودیت ۱۰۰ رویداد در snapshot فعلی می‌تواند برای مأموریت‌های بسیار طولانی بخشی از تاریخچه قدیمی را نشان ندهد؛ داده اصلی دیتابیس همچنان وجود دارد.
- آدرس/تلفن برخی فروشندگان مسابقه ساختگی و استعلام‌ها **فقط شبیه‌سازی** هستند.
