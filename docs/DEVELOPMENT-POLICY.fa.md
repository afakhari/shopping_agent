# سیاست توسعه سریع و تضمین کیفیت نسخه نهایی

**مصوب ۲۲ اکتبر ۲۰۲۶. اولویت اول: سرعت رسیدن به نسخه نهایی خوب؛ نه سبزکردن دائمی CI هنگام توسعه.**

## تعریف موفقیت
هدف یک تجربه خرید حضوری کامل، قابل‌فهم، موبایل‌محور، RTL و قابل‌اطمینان در زمان داوری است. ایرادهای موقت شاخه‌های کاری و نسخه آزمایشی پذیرفته‌اند، اما خطای شناخته‌شده بحرانی، نقض محدودیت‌های خرید، نشت اطلاعات محرمانه، یا سناریوی اصلی نیمه‌تمام در نسخه نهایی قابل‌قبول نیستند.

## سیاست شعبه‌ها و ادغام
- برای کارهای درشت از شاخه کاری با PR به صورت Draft استفاده شود. روی هر تغییر کوچک PR و commit اضافی ساخته نشود؛ یک برش قابل‌نمایش از محصول کافی است.
- لازم نیست در طول توسعه همه تست‌ها سبز بمانند. عیب‌های موقت در Issue/PR یادداشت شوند تا گم نشوند.
- برای تغییرات ساده‌ای که فوراً قابل‌برگشت‌اند، بازرسی انسانی و بررسی محلی متناسب کافی است.
- قبل از ادغام تغییر بزرگ در main، روی **آخرین commit تغییرات** یک اجرای کامل معتبر داشته باشید. Draft PR را بعد از تثبیت کد Ready for review کنید تا آزمون اجرا شود.
- بعد از هر اصلاح مجدد PR که قبلاً Ready شده، CI **به‌طور خودکار تکرار نمی‌شود**. پیش از ادغام به‌صورت دستی روی ref مناسب اجرا یا یک رویداد Ready for review جدید تولید کنید و شواهد مربوط به commit جدید را بررسی کنید.
- ادغام یا انتشار با شکست مشخص در سناریوی اصلی مجاز نیست.

## سیاست اجرای GitHub Actions
فقط یک Workflow جامع به نام `quality-gates` داریم که این حالت‌ها را پوشش می‌دهد:
1. **Manual:** از GitHub > Actions > quality-gates > Run workflow، انتخاب شاخه و اجرا در یک checkpoint مهم.
2. **PR ready_for_review:** وقتی Draft PR به Ready تبدیل شود، یک بار برای بازبینی اجرا می‌شود.
3. **Release tag:** با push یک tag مطابق `v*`، اجرا می‌شود.

به‌صورت پیش‌فرض هیچ اجرای خودکاری برای `push` عادی روی feature/main، تغییرات پیاپی یک PR یا PR Draft نداریم. عملیات پشت سر هم روی یک ref، اجرای قدیمی‌تر را لغو می‌کنند. workflow قدیمی `blueprint-sanity` جداگانه حذف و آزمون آن داخل quality-gates ادغام می‌شود.

**توجه درباره branch protection:** اجرای `workflow_dispatch` به‌تنهایی ممکن است به‌عنوان required status check برای PR شناخته نشود. در صورتی که GitHub روی main چک اجباری داشته باشد، از رویداد `ready_for_review` برای آخرین کد آماده ادغام استفاده شود. آزمون کامل نهایی پیش از release tag ضروری است، چون آزمون روی خود tag پس از ساخت آن نیز اجرا می‌شود.

## سه سطح بررسی
### توسعه سریع (هر تغییر)
- بررسی بصری همان قابلیت، سرور محلی، بررسی تغییرهای واضح و خطاهای runtime مرتبط.
- اگر لازم بود فقط test همان فایل/ماژول اجرا شود.
- هیچ الزام به CI برای هر commit وجود ندارد.

### checkpoint یا پایان یک قابلیت بزرگ
- اجرای سناریوی end-to-end آن قابلیت، چک‌های مرتبط، screenshot موبایل و ثبت خطاهای باز.
- quality-gates دستی فقط در صورت تغییر بزرگ و آماده بودن برش محصول.

### قفل کیفیت پیش از تحویل مسابقه
- full CI با آخرین commit قابل‌انتشار و بدون خطا.
- import واقعی دیتاست، migrations، اجرای مرورگر روی موبایل و دسکتاپ.
- ۲۰ حالت لبه‌ای، ۱۲ مسیر یکپارچه، map fallback، وضعیت تماس فروشنده و idempotency.
- تست امنیت پایه و عدم نشر کلیدها، محدودیت دسترسی به مأموریت‌ها.
- تست پایداری استقرار، latency، قابلیت بازیابی بعد از refresh و قطع اتصال.
- ویدئوی ۵ دقیقه‌ای ضبط‌شده از همان نسخه مستقر، نه فقط mock.
- هنگام قطع قابلیت مهم، release را متوقف کنید. راه‌حل ترجیحی اصلاح یا غیرفعال‌کردن شفاف قابلیت ناقص، نه نمایش خروجی ساختگی.

## تفکیک تست‌های واقعی از تست‌های CI
سبزبودن quality-gates **فقط** تست Node/Python، تست‌های مخزن، اسناد و PostgreSQL CI را اثبات می‌کند. این Workflow جای سنجش UX روی مرورگر واقعی، صحت دیتاست خام مسابقه، کلید نقشه، استعلام شبیه‌سازی واقعی و استقرار عمومی را نمی‌گیرد.

## حفظ سرعت
- برای یک تغییر UX در ابتدا طرح و fixture اجرا کنید، سپس بعد از تثبیت رفتار build نهایی.
- بدون benchmark سراغ تغییر معماری، موتور جست‌وجوی جدید یا multi-agent نروید.
- قبل از انتشار اطلاعات حساس و عملیات دارای اثر خارجی باید ایمن باشند؛ امنیت را نمی‌توان به انتهای توسعه موکول کرد.
- تمرکز روی تکمیل مسیر کاربر است، نه تعداد فایل یا green badge.
