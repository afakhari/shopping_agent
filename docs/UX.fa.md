# طراحی UX | Mobile-first RTL

## IA و مرحله‌ها
Home / Discovery / Compare Products / Explore Shops / Contact & Verify / Visit Plan. این‌ها وضعیت‌های مأموریت هستند و الزاماً routeهای جدا یا Wizard اجباری نیستند.

## سیاست ناوبری آزاد و غیرخطی
- مراحل بالا **نقشهٔ قابلیت‌ها** هستند، نه نوار پیشرفت، فرم چندمرحله‌ای یا ترتیبی که کاربر ملزم به پیروی از آن باشد. نوار دائمی چهارگامی بالای گفتگو نباید نمایش داده شود؛ این الگو پیش‌تر در بازخورد واقعی کاربر رد و از DOM حذف شده است.
- اگر کاربر مدل مشخصی می‌داند، مستقیم آفرها و فروشندگان واجد شرایط را ببیند؛ مقایسهٔ چند محصول یا پرسش دربارهٔ نیازمندی‌ها پیش‌شرط نیست.
- کاربر می‌تواند مستقل از هر «مرحله» مقایسه کند، بودجه/محدوده/اعتبار را ویرایش کند، به فهرست قبلی برگردد یا بدون اجرای استعلام نمایشی متوقف شود.
- استعلام فروشنده صرفاً با اقدام صریح او انجام می‌شود؛ برنامهٔ مراجعه فقط وقتی شواهد و انتخاب معتبر کافی وجود دارند ارائه می‌شود، نه برای پر کردن گام بعدی یک نوار.
- راهنمای کوتاهِ مرتبط با همان نتیجه و CTA واضح درون کارت پذیرفتنی است؛ «قدم ۱ از ۴» یا نشانگر «مراحل انجام‌شده» در هدر از رفتار غیرخطی مأموریت نتیجه نمی‌شود.

## Home
یک ورودی محاوره‌ای اصلی، سه نمونه مرتبط، کنترل اختیاری منطقه و بودجه. هیچ نقشه یا فیلتر طولانی پیش از جست‌وجو نمایش داده نشود.

## Discovery
۲ تا ۴ مدل منتخب با عکس، مشخصات تعیین‌کننده، برچسب دلیل پیشنهاد، قیمت ثبت‌شده و تعداد فروشنده. فیلترهای مختص دسته محصول. پرسش تکمیلی فقط اگر پاسخ بدون آن معنادار نباشد.

## Compare
حداکثر ۳ محصول، جدول اختلاف‌های مهم پیش‌فرض، قابلیت «نمایش همه مشخصات»، مدیریت unknown و انتخاب نهایی با یک اقدام واضح.

## Explore Shops
روی موبایل سوئیچ List / Map و bottom sheet. روی دسکتاپ نقشه و لیست هماهنگ. chip فیلترهای فعال با حذف جداگانه. قیمت، تاریخ بروزرسانی، فاصله مستقیم، زمان سفر (فقط با API معتبر)، بازبودن طبق برنامه، روش خرید اعتباری و گارانتی. مرتب‌سازی با گزینه‌های «مناسب‌ترین»، «ارزان‌ترین» و «نزدیک‌ترین» که منطقشان مستند باشد.

## Contact
پس از تأیید کاربر، اسکریپت تماس شبیه‌سازی: پرسش قیمت، موجودی، زمان مراجعه. حالت‌های pending, confirmed, unavailable, no_answer, price_changed, closed, error. نشان دادن نتیجه و مرحله بعد بدون آوار پیام‌های فنی.

## Visit Plan
کارت مستقل با product id / shop id / verified outcome / updated price if any / address details / opening hours / navigation / backup seller. CTA اصلی «مشاهده مسیر» و امکان «تغییر فروشنده».

## اصول بصری
Vazirmatn و bidi مناسب شماره مدل/قیمت؛ اندازه مناسب لمس، contrast و visible focus، reduced-motion، Empty/Error/Skeleton. فیلترهای موبایل با دکمه «نمایش نتایج» در صورت چند انتخاب متوالی.

## رفتار در لبه‌ها
- رد مجوز مکان → انتخاب دستی محدوده.
- نبود نتیجه → علت محدودیت، پیشنهاد تغییر یک شرط با کنترل کاربر.
- فروشگاه فقط دسته مرتبط دارد → به‌عنوان دارنده محصول معرفی نشود.
- ساعات نامعلوم → «نامشخص»، نه «باز».
- نقشه در دسترس نیست → لیست و آدرس باقی بماند.
- صفحه تازه‌سازی شد → snapshot مأموریت از سرور بازیابی شود.
- پاسخ دیررس قدیمی → با request id و abort از overwrite جلوگیری شود.
- عدم پاسخ فروشنده → جایگزین هم‌محصول با حفظ شروط.
- شکست جایگزین → تغییر شروط فقط با رضایت.


## بازخورد واقعی و وضعیت UX در ۲۳ اکتبر ۲۰۲۶
- تصویر واقعی کاربر نشان داد «احوال شما؟» به‌اشتباه ۱۲۰ کالای نامرتبط، از جمله لوازم آرایش و تیغ جراحی، بازگردانده بود. این UX و تشخیص نیت، نه خرابی دیتاست، بود.
- PR #25 در UI و API از ورود احوال‌پرسی خالص به جست‌وجو/BoxAPI جلوگیری می‌کند و هنگام بازخوانی تاریخچه، کارت‌های اشتباه قدیمی را در نمایش پنهان می‌کند. **آزمون خودکار در Chromium مصنوعی موفق شد**؛ بررسی دوباره روی مرورگر محلی کاربر هنوز گزارش نشده است.
- PR #24 فرم نتیجه خالی را ساده، پس از سلام/تشکر قابل استفاده و در تاریخچه چند تلاش قبلی جمع‌وجور کرد. خطای 502/429، SSE ناقص، بازیابی snapshot و idempotent contact نیز پوشش تست دارند.
- CI مرورگر در ۳۲۰/۳۹۰/۱۴۴۰ روی داده مصنوعی موفق است؛ آزمون دستی روی ۳۶۰px، تلفن واقعی، axe/keyboard با کاربر و مقایسه بصری همه سناریوهای داده اصلی هنوز باز است.
- اصل UX: درخواست اجتماعی نباید کارت محصول یا آمار «نتیجه» بسازد؛ شکستن قیود خرید بدون اختیار کاربر ممنوع؛ استعلام فروشنده **صرفاً دمو** است.
