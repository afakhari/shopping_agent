# ممیزی دیتاست Starcoach v16 cap300

**زمان ثبت ممیزی:** 2026-10-21.
**منبع:** فایل `starcoach-dataset-v16-cap300-csv.zip` آپلودشده؛ آرشیو شامل `README.txt`, `products.csv`, `shops.csv`, `offers.csv` است. حجم uncompressed گزارش‌شده در فهرست ZIP حدود 285 MB است. این گزارش مربوط به همین نسخه فایل است و با dataset تازه‌تر باید دوباره تولید شود.

## خلاصه اجرایی

| فایل | تعداد ردیف | ستون |
|---|---:|---:|
| `products.csv` | 225,903 | 7 |
| `shops.csv` | 6,476 | 13 |
| `offers.csv` | 331,506 | 8 |
| **کل** | **563,885** | — |

شناسه‌های هر فایل در بررسی اولیه یکتا بودند و در اتصال آفرها به محصول/فروشگاه orphan مشاهده نشد. این یک یافته برای snapshot فعلی است، نه جایگزین constraint در دیتابیس یا تست import.

## 1. محصولات

- عنوان فارسی non-empty: 225,901؛ دو رکورد عنوان خالی.
- برند non-empty: 57,634؛ برند برای تعداد زیادی محصول ثبت نشده.
- مدل non-empty: 4,056؛ `model` به تنهایی برای شناسایی کافی نیست.
- تصویر: 224,684 محصول آرایه تصویر غیرخالی؛ 1,219 محصول بدون تصویر.
- `specs` در همه ردیف‌ها به شکل JSON array قابل خواندن بود، اما 81,304 محصول آرایه مشخصات خالی دارند.
- 3,428 دسته متفاوت مشاهده شد.
- نمونه ویژگی `specs`: عناصر `{key, section, value}` با مقادیر رشته‌ای؛ همه ویژگی‌ها عددی یا هم‌معنا نیستند.

**نتیجه طراحی:** جست‌وجوی تصویری می‌تواند P1 باشد، اما فعلاً جست‌وجوی متنی و مقایسه مشخصات ثبت‌شده اولویت دارند. مقایسه فنی باید روی کلیدهای همسان/سازگار انجام شود، نه تشابه دلخواه رشته‌ها.

## 2. فروشگاه‌ها

- 6,476 رکورد مختصات latitude/longitude غیرخالی دارند.
- 6,475 آدرس متنی و 6,475 `location_label` غیرخالی دارند.
- 3,179 آدرس شامل «پاساژ»؛ 4,224 شامل «طبقه»؛ 2,380 شامل «واحد» هستند. این شمارش‌ها مستقل‌اند و هم‌پوشانی دارند.
- 90 وب‌سایت و 22 حساب اینستاگرام ثبت شده‌اند؛ مجموع فروشگاه‌های دارای یکی از این دو نوع منبع 112 است.
- `contacts` در هر 6,476 رکورد یک array دارد؛ بر اساس توضیح برگزارکننده، شماره‌ها برای شبیه‌سازی‌اند و عملیات دمو باید از simulator استفاده کند.
- داده ورودی برای تهران انتخاب شده؛ CSV فیلد مستقل city ندارد.
- از 6,476 فروشگاه، 3,792 فروشگاه حداقل یک آفر دارند. داشتن shop row یا دسته فعالیت به معنی عرضه محصول مشخص نیست.

**نتیجه طراحی:** آدرس و مختصات برای نقشه پایه مفیدند. تشخیص طبقه/واحد از متن یک feature ارزشمند است؛ ولی مسیر داخل راهروهای پاساژ در این دیتاست تضمین نشده.

## 3. گزینه‌های پرداخت

- 6,476 `payment_options` به شکل JSON array parse شدند.
- 266 فروشگاه array غیرخالی دارند.
- در کل arrayها، 385 گزینه پرداخت مشاهده شد: 174 با `channel=in_person` و 211 با `channel=unknown`.
- 82 فروشگاه حداقل یک گزینه `in_person` دارند.
- در snapshot ممیزی، هم‌پوشانی آن 82 فروشگاه با 112 فروشگاه دارای وب‌سایت/اینستاگرام ثبت‌شده صفر بود.

این هم‌پوشانی صفر یعنی نباید سناریوی تماس/وب‌سایت رسمی را بدون تست داده واقعی با شرط خرید اعتباری حضوری ترکیب کنیم. قابلیت فیلتر را پیاده می‌کنیم، ولی برای دمو باید سناریویی انتخاب شود که نتیجه واجد شرایط واقعی در همین داده داشته باشد.

قواعد eligibility:

- `in_person` = واجد شرط پذیرش حضوری صریح.
- `unknown` = برای شرط سخت حضوری واجد شرایط نیست.
- array خالی/اطلاعات غایب = وضعیت ثبت نشده؛ در فیلتر سخت وارد نتایج نمی‌شود.
- عدم وجود record را به‌صورت «مطمئناً قبول نمی‌کند» توضیح ندهیم؛ فقط برای شرط درخواست‌شده نتیجه مناسب نیست.

## 4. ساعت کاری

`weekly_hours` در هر 6,476 رکورد یک JSON object است؛ ممکن است `{}` باشد. در روزهای تعریف‌شده، statusهای مشاهده‌شده:

| status | تعداد رخداد روزانه در objectها |
|---|---:|
| `declared` | 27,270 |
| `closed` | 4,006 |
| `unsupported` | 35 |

این شمارش رخداد روزهاست، نه تعداد فروشگاه‌ها. هرگز ساعات خالی یا `unsupported` را open فرض نکنید. تبدیل روزهای هفته به تاریخ/ساعت و شیفت عبوری از نیمه‌شب باید تست داشته باشد.

## 5. آفرها و قیمت

- 316,423 آفر `price_toman` non-empty دارند؛ 15,083 فاقد قیمت.
- 330,737 آفر timestamp non-empty دارند؛ 769 فاقد آن هستند.
- timestamp قدیمی مشاهده‌شده: `2020-12-03T08:51:32.129814+00:00`.
- جدیدترین timestamp مشاهده‌شده: `2026-10-13T00:02:35.297834+00:00`.
- بر مبنای 2026-10-21، timestamp جدیدتر از هفت روز گذشته مشاهده نشده است؛ این به معنی قدیمی‌بودن همه آفرها به یک اندازه نیست.
- 144 مقدار قیمت بزرگ‌تر از 100 میلیارد تومان مشاهده شد. عدد بزرگ لزوماً همیشه غلط نیست؛ باید در quality flag قرار گیرد و با قواعد دسته‌ای بررسی شود.
- timestamp، قیمت و موجودی مستقل‌اند. داده فعلی موجودی زنده ندارد.
- warranty: 58,943 آفر object غیرnull دارند؛ 272,563 مقدار `null`/غایب.
- description فروشنده در حدود 88٪ آفرها خالی است؛ warranty نیز غالباً خالی است.

### Policy کیفیت قیمت

1. قیمت تهی را صفر نکن.
2. `float` را برای قیمت استفاده نکن.
3. رقم پرت را silently اصلاح نکن؛ raw را حفظ و quality flag ثبت کن.
4. تا زمانی که policy دسته‌ای پیاده و تست نشده، قیمت extreme را از مرتب‌سازی/بهترین قیمت پیش‌فرض حذف کن؛ در صورت لازم برای debug قابل ردیابی باشد.
5. threshold 100 میلیارد فقط سیگنال بازبینی ابتدایی این snapshot است، نه قاعده دائمی همه دسته‌ها. threshold نهایی باید configurable و مستند باشد.
6. زمان منبع را به `Asia/Tehran` برای نمایش تبدیل کن، ولی timestamp UTC اصلی را حفظ کن.

## 6. روابط و محدودیت کاتالوگ

- هر 225,903 محصول در این snapshot حداقل یک آفر دارند.
- سقف cap300 طبق README ورودی یعنی تعداد محصول متمایز در هر فروشگاه حداکثر 300 محدود شده است؛ این دیتاست نماینده کامل بازار تهران نیست.
- همه رکوردهای shops به‌عنوان فروشگاه تهران انتخاب شده‌اند، ولی پوشش محله‌ها گزینشی است.
- ردیف آفر به کلیدهای product_id و shop_id متصل است؛ idهای یتیم در بررسی اولیه مشاهده نشدند.

## 7. نتیجه کنترل پیش از ورود به کد

در بررسی مستقل با Python استاندارد، سه CSV کامل پیمایش شدند: `products.csv` دارای 225,903 ردیف، `shops.csv` دارای 6,476 ردیف و `offers.csv` دارای 331,506 ردیف بود. در همان snapshot، شناسه خالی/تکراری، JSON نامعتبر در فیلدهای nested بررسی‌شده، آفر دارای product/shop ناموجود، قیمت غیرقابل‌تبدیل به عدد صحیح یا timestamp غیرقابل‌تبدیل مشاهده نشد. این نتیجه، اعتبارسنجی خام فایل‌هاست و اجرای importer یا migrationهای Django را اثبات نمی‌کند.

## 8. اقدامات بعدی برای تکرار ممیزی

Import tool باید خلاصه کیفیت قابل تکرار تولید کند: تعداد ردیف، unique IDs، FK orphans، JSON parse errors، nulls per field، قیمت‌های نامعتبر/پرت، توزیع timestamp، shops with offers، options by channel و پوشش تصاویر/specs. خروجی summary باید به شکل JSON/Markdown قابل ذخیره باشد. اعداد بالا را هنگام تغییر فایل ورودی دوباره محاسبه کنید؛ از hardcodeکردن این شمارش‌ها در منطق تجاری اجتناب شود.
