# مشخصات UX و رابط کاربری

## 1. جهت طراحی

محصول موبایل‌محور و فارسی/RTL است. زبان بصری باید آرام، قابل‌اعتماد و کاربردی باشد؛ اطلاعات کلیدی قبل از تزئینات بصری قرار می‌گیرند. هدف این نیست که همه تعامل‌ها چت باشند. فرم و فیلتر، کارت و نقشه ابزارهای اصلی تجربه‌اند.

## 2. معماری صفحه

### صفحه شروع / جست‌وجو

- عنوان کوتاه و ورودی متن طبیعی.
- promptهای نمونه یا پیشنهادهای شروع؛ نه بخش‌های طولانی متنی.
- فیلترهای سریع و قابل جمع‌شدن: بودجه، خرید اعتباری حضوری، مبدأ/شعاع، مرتب‌سازی.
- شهر به‌صورت پیش‌فرض تهران و قابل مشاهده؛ اگر شهر دیگری در دیتاست نیست، نتایج تهران به آن شهر نسبت داده نشود.

### نتایج محصول

- تصویر (اگر وجود دارد)، عنوان، برند در صورت موجودبودن، دسته و چند مشخصه مرتبط.
- ارزان‌ترین **آفر واجد شرایط** به‌عنوان نقطه ورود، با قیمت ثبت‌شده و تاریخ تغییر.
- شمار فروشندگان واجد شرایط و action مقایسه.
- کارت محصول هیچ‌گاه قیمت را بدون واحد تومان نمایش ندهد.

### مقایسه فروشندگان

- جدول در دسکتاپ، کارت‌های قابل اسکرول عمودی در موبایل.
- معیارها: قیمت ثبت‌شده، زمان آخرین تغییر، آدرس، فاصله/زمان مسیر با برچسب درست، پرداخت حضوری و نتیجه استعلام.
- مقایسه باید مقدار `unknown` را به‌عنوان unknown نشان دهد، نه false/true.
- کنترل مرتب‌سازی همیشه در دسترس باشد.

### پرونده «پیش از حرکت»

خروجی نهایی خرید: کالا، فروشگاه اصلی، جایگزین، آدرس، طبقه/واحد/پاساژ از متن منبع، قیمت و زمان آن، شرایط پرداخت، وضعیت استعلام، لینک نقشه و کار باقی‌مانده. این summary باید به تنهایی کاربردی باشد و نیازمند خواندن مکالمه نباشد.

## 3. رفتار فیلترها

- هر فیلتر تغییرشده یک query جدید به API می‌فرستد؛ debounce جست‌وجوی متن می‌تواند 250–350ms باشد، پس از benchmark اصلاح شود.
- درخواست قبلی لغو می‌شود (`AbortSignal`) و race condition نباید نتیجه کهنه را روی نتیجه تازه overwrite کند.
- فیلترهای قطعی در server اجرا می‌شوند؛ UI صرفاً visibility را دستکاری نکند.
- برای «پذیرش اعتباری حضوری»، only `channel=in_person` واجد شرایط است.
- اگر تعداد نتایج صفر شد، کارت‌های نامنطبق نمایش داده نمی‌شوند؛ پیشنهاد تغییر شرط با توضیح اثر در دسترس قرار می‌گیرد.
- هر پیشنهاد تغییر شرط باید انتخابی باشد. UI نباید بودجه یا محدوده را خودکار گسترش دهد.

## 4. حالت‌های لازم هر component

تمام صفحه‌ها/کامپوننت‌های داده‌محور باید حالت‌های زیر داشته باشند:

- idle/default
- loading/skeleton
- success
- empty with next step
- recoverable error with retry
- fatal/blocked error with explanation
- stale/partial data در صورت کاربرد

برای stream مأموریت: connecting, running stage, tool action, completed, interrupted/reconnect, failed with fallback.

## 5. کپی UX و واژگان ثابت

واژگان پیشنهادی برای یکپارچگی:

- «قیمت ثبت‌شده» = مقدار از `Offer.price_toman`.
- «آخرین تغییر قیمت» = `last_price_changed_at`.
- «موجودی تأیید شد» فقط با نتیجه تأیید معتبر ابزار.
- «موجودی نامشخص» وقتی هیچ شواهد تازه‌ای وجود ندارد.
- «نتیجه استعلام در سناریوی دمو» برای آشکارکردن شبیه‌سازی در کانتکست ارزیابی، نه هشدار تکراری در همه صفحه‌ها.
- «فروشگاه واجد شرایط» یعنی شروط hard جاری را پاس کرده است؛ این عبارت به تنهایی تایید موجودی نیست.
- «فاصله مستقیم» برای فاصله مختصاتی؛ «زمان مسیر» تنها از route provider.

## 6. RTL، تایپوگرافی و اعداد

- ریشه صفحه `dir="rtl"`; اجزای ورودی، جدول، dialog و dropdown نیز تست شوند.
- استفاده از CSS logical properties (`margin-inline`, `padding-inline`, `inset-inline`) به‌جای left/right غیرضروری.
- شناسه/URL/شماره تماس در span با جهت `ltr` در صورت نیاز.
- مبلغ از رشته رقم‌ها parse و با Intl.NumberFormat نمایش داده شود؛ هیچ مبلغی از `Number(priceString)` اگر می‌تواند از safe integer بیشتر باشد تبدیل نشود.
- متن‌های بلند فروشنده truncate همراه با امکان مشاهده کامل.
- state focus، keyboard navigation و contrast قابل قبول رعایت شود.

## 7. نقشه و موقعیت

- نقشه و list باید انتخاب متقابل داشته باشند: انتخاب pin کارت را highlight کند و انتخاب کارت pin را.
- در موبایل، نقشه می‌تواند به تب «نقشه/فهرست» تبدیل شود؛ نقشه نباید فضای محتوای مهم را بگیرد.
- عدم دسترسی به map provider: فهرست و نشانی همچنان قابل‌استفاده باشند.
- مختصات بدون route provider برای زمان پیاده‌روی استفاده نشوند.
- آدرس داخل پاساژ تنها از منبع متنی استخراج شود؛ مسیر راهرو/طبقه دقیق از حدس تولید نشود.

## 8. کنترل‌های عامل

- stage indicator باید کار معنی‌دار انجام‌شده را نشان دهد؛ انیمیشن با ادعای «در حال تماس» پیش از آغاز ابزار ممنوع.
- کاربر بتواند نتیجه را اصلاح کند، فیلتر تغییر دهد یا پیشنهاد جایگزین را برگزیند.
- نمایش chain-of-thought یا reasoning مخفی ممنوع؛ فقط خلاصه دلیل قابل‌فهم و مستند به داده نمایش داده شود.
- دکمه‌های اقدام باید عمل واقعی داشته باشند و در loading disable شوند.
- خطای ابزار با اقدام بعدی توضیح داده شود؛ از متن خام exception پرهیز شود.

## 9. معیار کیفیت UX

- جریان اصلی با ماوس، لمس و صفحه‌کلید قابل اجرا باشد.
- روی viewport موبایل معمول، محتوای اصلی اسکرول افقی نداشته باشد.
- خطای API باعث از دست رفتن فیلترهای کاربر نشود.
- نتایج غیرواجد شرایط در UI اصلی وجود نداشته باشند.
- کاربر بتواند انتخاب اصلی و جایگزین را بدون شروع دوباره مقایسه کند.
