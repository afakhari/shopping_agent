# راهنمای کامل راه‌اندازی و راستی‌آزمایی در Windows

این راهنما برای اجرای محلی نسخه فعلی Bazaar Compass روی Windows 10/11 نوشته شده است. هدف آن این است که توسعه‌دهنده بتواند با اجرای دستورهای مشخص، وابستگی‌ها را نصب کند، آزمون‌ها را اجرا کند، دیتاست را بررسی و وارد کند و نسخه وب را در مرورگر ببیند.

> وضعیت فعلی: کد و قراردادها در ZIP تحویلی قرار دارند، اما در محیط تولیدکننده پروژه، دسترسی به Docker و رجیستری npm/PyPI وجود نداشت؛ در نتیجه آزمون کامل runtime هنوز تأیید نشده است. اسکریپت زیر برای انجام این مرحله روی کامپیوتر توسعه‌دهنده آماده شده است.

## 1. آنچه باید از قبل نصب باشد

1. **Python 3.13 x64** با Python Launcher (`py`). دانلود: <https://www.python.org/downloads/windows/>.
2. **Node.js 22.12 یا جدیدتر**؛ نسخه LTS مناسب است. دانلود: <https://nodejs.org/>.
3. **Docker Desktop برای Windows** با پشتیبانی Docker Compose. دانلود: <https://www.docker.com/products/docker-desktop/>. بعد از نصب، Docker Desktop را اجرا کن.
4. PowerShell 5.1 یا PowerShell 7.
5. اتصال اینترنت در اولین نصب برای دریافت وابستگی‌های Python و npm.

پس از نصب، یک پنجره PowerShell تازه باز کن و بررسی کن:

```powershell
py -3.13 --version
node --version
npm.cmd --version
docker version
docker compose version
```

اگر `docker version` به daemon وصل نمی‌شود، ابتدا Docker Desktop را باز کن و تا آماده‌شدن موتور آن صبر کن؛ لازم نیست هیچ کاری در ChatGPT انجام دهی.

## 2. استخراج پروژه و قرار دادن دیتاست

1. بسته کامل پروژه با نام `bazaar-compass-local-verification.zip` را از همین گفت‌وگو دانلود کن؛ این بسته شامل آخرین تغییرات اسکریپت راه‌اندازی و گزارش ممیزی است.
2. محتوای ZIP را در یک مسیر ساده، مثلاً `D:\projs\bazaar-compass` استخراج کن. در پایان باید مسیر `D:\projs\bazaar-compass\README.md` و پوشه‌های `backend`, `frontend`, `docs`, `scripts` وجود داشته باشند.
3. فایل `starcoach-dataset-v16-cap300-csv.zip` را هم دانلود کن.
4. در ریشه پروژه پوشه `data` را بساز و ZIP دیتاست را دقیقاً با این مسیر قرار بده:

```text
D:\projs\bazaar-compass\data\starcoach-dataset-v16-cap300-csv.zip
```

ZIP اصلی را لازم نیست دستی استخراج کنی. importer خود برنامه آن را می‌خواند. اسکریپت audit نیز ZIP یا یک پوشه شامل هر سه CSV را می‌پذیرد.

**مهم:** ZIP دیتاست، CSVها، `.env` و کلیدهای API نباید به Git اضافه شوند. الگوی `.gitignore` فعلی آن‌ها را کنار می‌گذارد.

## 3. اجرای بررسی‌ها به‌صورت خودکار

در PowerShell وارد ریشه پروژه شو:

```powershell
Set-Location D:\projs\bazaar-compass
```

اگر سیاست اجرای PowerShell اجازه اجرای اسکریپت محلی را نمی‌دهد، فقط برای همین پنجره اجرا کن:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```

سپس تمام بررسی‌های محلی را اجرا کن:

```powershell
.\scripts\verify-local.ps1
```

این دستور:

- محیط مجازی Python را در `backend\.venv` می‌سازد.
- وابستگی‌های توسعه را نصب می‌کند.
- `manage.py check`، بررسی سازگاری migrationها، pytest و Ruff را اجرا می‌کند.
- با `npm install` اولین `package-lock.json` را می‌سازد یا در اجراهای بعدی با `npm ci` همان lockfile را نصب می‌کند. این lockfile را در نسخه کنترل‌شده پروژه نگه دار؛ ZIPهای تحویلی به‌دلیل نبود دسترسی npm در محیط سازنده، lockfile را شامل نمی‌شوند.
- lint، typecheck، آزمون‌های Vitest و build فرانت‌اند را اجرا می‌کند.
- در صورت وجود دیتاست، گزارش کیفیت مستقل و dry-run سخت‌گیرانه importer را اجرا می‌کند.

اولین نصب ممکن است به اینترنت و زمان بیشتری نیاز داشته باشد. اگر اسکریپت در یک مرحله خطا دهد، متوقف می‌شود؛ متن کامل خطای اولین دستور ناموفق را نگه دار. از اجرای چند نصب موازی یا حذف کورکورانه پوشه‌های محیط مجازی خودداری کن.

گزارش ممیزی دیتاست در `reports\dataset-audit.md` و `reports\dataset-audit.json` تولید می‌شود. importer نیز شمارش رکوردها و گزارش ورود را چاپ می‌کند.

## 4. ساخت و اجرای کل برنامه با Docker

پس از گذر موفق از تست‌های محلی و وجود فایل دیتاست، اجرا کن:

```powershell
.\scripts\verify-local.ps1 -SkipPython -SkipFrontend -WithDocker -ImportDataset
```

این فرمان مرحله نصب و تست محلی را تکرار نمی‌کند؛ Compose را بررسی می‌کند، imageها را می‌سازد، سرویس‌ها را بالا می‌آورد، منتظر readiness بک‌اند می‌ماند، importer را ابتدا در حالت dry-run اجرا می‌کند و سپس دیتاست را به PostgreSQL محلی وارد می‌کند. در انتها endpoint جست‌وجو را smoke-test می‌کند.

اسکریپت، در صورت نبود `.env`، آن را از `.env.example` می‌سازد. مقادیر پیش‌فرض صرفاً برای اجرای محلی هستند و نباید در دیپلوی عمومی استفاده شوند.

اگر فقط `-WithDocker` را بدون `-ImportDataset` اجرا کنی، دیتاست وارد پایگاه داده نمی‌شود و آزمون جست‌وجو عمداً رد می‌شود؛ برای تست واقعی کاتالوگ باید `-ImportDataset` هم بدهی.

پس از موفقیت:

- رابط کاربری: <http://localhost:8080>
- readiness بک‌اند از طریق Nginx: <http://localhost:8080/api/v1/health/ready/>
- جست‌وجوی نمونه: <http://localhost:8080/api/v1/catalog/search/?q=%D9%87%D8%AF%D9%81%D9%88%D9%86&page=1&page_size=5>

اگر در `.env` مقدار `APP_PORT` تغییر کرده است، به‌جای `8080` از همان پورت استفاده کن.

برای مشاهده لاگ‌ها:

```powershell
docker compose logs --tail 150 backend
docker compose logs --tail 150 frontend
docker compose logs --tail 100 db
```

برای توقف سرویس‌ها، بدون پاک‌کردن داده دیتابیس:

```powershell
docker compose down
```

**داده دیتابیس پاک نمی‌شود** مگر آنکه volume را جداگانه حذف کنی. دستور `docker compose down -v` داده PostgreSQL را پاک می‌کند؛ آن را برای عیب‌یابی عادی اجرا نکن.

## 5. فعال‌سازی اختیاری مدل زبانی

نسخه کاتالوگ و parser قطعی بدون API key باید کار کند. مدل زبانی برای فهم بهتر درخواست فارسی اختیاری است و برای اولین تست لازم نیست کلید تهیه کنی.

پس از آنکه UI، جست‌وجو، importer و تست‌ها موفق شدند، `.env` را با ویرایشگر محلی باز کن و موارد زیر را مطابق provider خود تنظیم کن:

```dotenv
LLM_ENABLED=1
LLM_PROVIDER=openai_compatible
LLM_API_KEY=کلید-واقعی-فقط-در-فایل-محلی
LLM_MODEL=نام-مدل-پشتیبانی-شده
LLM_BASE_URL=https://api.openai.com/v1
LLM_TIMEOUT_SECONDS=6
```

- آدرس پایه باید endpoint سازگار با `POST /chat/completions` را فراهم کند.
- از provider، مدل و API keyای استفاده کن که حساب تو واقعاً به آن دسترسی دارد.
- کلید را در چت، README، کد فرانت‌اند یا `VITE_*` وارد نکن.
- پس از تغییر env، سرویس بک‌اند را بازسازی/راه‌اندازی مجدد کن:

```powershell
docker compose up -d --force-recreate backend
```

- اگر provider دسترس‌پذیر نبود یا timeout رخ داد، parser قطعی باید فعال بماند. برای ارزیابی منصفانه، خروجی parser و زمان پاسخ را در لاگ بررسی کن.

**هیچ کلید یا رمز خود را برای من ارسال نکن.** اگر نیاز به کمک است، نام provider، مدل و پیام خطا را بدون secret بفرست.

## 6. سناریوی آزمون دستی پس از راه‌اندازی

1. در رابط، درخواست فارسی کوتاهی مثل «یک هدفون بی‌سیم تا سقف ۳ میلیون تومان می‌خواهم» ثبت کن.
2. بررسی کن فقط محصولات دارای آفر در دیتاست و منطبق با بودجه در نتایج اصلی ظاهر شوند.
3. شرط «فقط پذیرش اعتباری حضوری» را فعال کن و بررسی کن تعداد و نتیجه فهرست عوض شود؛ نتیجه صفر باید empty state درست داشته باشد، نه کالاهای نامنطبق.
4. از یک محصول «بررسی موجودی» را انتخاب کن. خروجی تماس باید به صراحت نشان دهد که سناریوی دمو بوده است.
5. پس از نتیجه‌هایی مانند عدم پاسخ یا ناموجود بودن، بررسی کن گزینه‌های جایگزین بودجه و شروط اعتباری/مکانی را رعایت کنند.
6. صفحه را refresh کن؛ شناسه مأموریت، فیلترهای خرید، نتایج آخر و پاسخ‌های شبیه‌سازی‌شده باید از snapshot بازیابی شوند. اگر دیتابیس/volume پاک شده باشد یا مأموریت وجود نداشته باشد، UI باید خطای بازیابی نشان دهد و امکان شروع مأموریت تازه بدهد.
7. DevTools → Network را باز کن و مطمئن شو درخواست‌های search بدون فراخوانی مدل انجام می‌شوند و کلید API در هیچ درخواست مرورگر دیده نمی‌شود.

## 7. چه خروجی‌ای را برای عیب‌یابی بفرستی؟

اگر مرحله‌ای شکست خورد، این اطلاعات کافی است:

- شماره مرحله یا آخرین عنوان `>>> ...` که اسکریپت چاپ کرد.
- متن کامل خطای همان مرحله و ۳۰ تا ۵۰ خط اطراف آن.
- خروجی `py -3.13 --version`, `node --version`, `npm.cmd --version`, `docker version` و `docker compose version`.
- اگر خطا در Docker است، خروجی `docker compose ps` و `docker compose logs --tail 100 backend`؛ قبل از ارسال، نام کاربری، URL خصوصی، مقدار env و هر secret احتمالی را حذف کن.

این‌ها را **نفرست**: `.env` کامل، API key، پسورد PostgreSQL یا فایل دیتاست کامل. دیتاست از قبل در اختیار پروژه است و برای خطای نصب نیازی به آپلود دوباره آن نیست.

## 8. تعریف «آماده بودن»

پروژه زمانی runtime-verified محسوب می‌شود که همه موارد زیر در محیط واقعی اجرا شوند:

- [ ] `manage.py check`
- [ ] `makemigrations --check --dry-run`
- [ ] کل pytest و Ruff
- [ ] `npm ci` (پس از تولید و نگهداری lockfile)، lint، typecheck، test و build
- [ ] Docker Compose clean build و healthcheck
- [ ] dry-run موفق importer و import واقعی به PostgreSQL
- [ ] search با نتایج واقعی، فیلتر بودجه، فیلتر اعتباری و empty-state
- [ ] استعلام شبیه‌سازی‌شده و بازیابی با جایگزین
- [ ] اتصال واقعی provider LLM فقط در صورت فعال‌کردن آن
- [ ] اجرای سناریوی دمو از ابتدا تا انتها در مرورگر

تست‌های syntax و `verify_scaffold.py` به‌تنهایی این معیار را برآورده نمی‌کنند.
